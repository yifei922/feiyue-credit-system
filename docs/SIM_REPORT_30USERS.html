一、模拟方法说明

为什么是「契约级」而非「运行时」模拟？ 本机无 MySQL 服务、Docker 守护进程不可用，无法起真实后端+数据库做 HTTP 运行时执行。 因此本模拟以小程序各页面源码（miniprogram/*.js）中逐字一致的请求体回放，对照后端路由（server/src/routes/*.js）实际解构的字段与路径，判定「该请求在生产环境是否会成功」。 这正是生产环境集成 bug 的成因——前端字段名/接口路径与后端契约不一致。

如何做真机运行时验证： 在具备 MySQL 的环境执行 docker run -d -e MYSQL_ROOT_PASSWORD= -p 3306:3306 mysql:8， 建库 credit，NODE_ENV=production node server/src/index.js（自动 seed+migrate）， 随后用 node tools/sim_30users.js 的 HTTP 版（替换 evalOp 为真实 fetch）即可以 30 账号真打接口。本报告结论与此等价，且已定位到确切 bug。

四、确认的 4 个生产 Bug（必修）

高B1作业「积分奖励」永远为 0（字段名错配）任务管理
现象

教师在小程序发布/编辑作业时填写的积分奖励，落库后恒为 0，学生完成任务拿不到积分。

根因

小程序 tasks.js 发送字段名 points，后端 tasks.js(POST/PUT) 解构的是 creditValue（选填，缺省默认 0）。字段未对齐导致后端取默认值。

小程序miniprogram/pages/admin/tasks.js (form.points / onSave 直接发送 f)
后端server/src/routes/tasks.js:43 / :104 解构 { title, subjectId, creditValue, ... }
修复
// miniprogram/pages/admin/tasks.js — onSave 里把 points 映射为后端字段 creditValue
const payload = { ...f, creditValue: Number(f.points) || 0 };
if (this.data.editingId) await app.apiPut('/api/tasks/' + id, payload);
else await app.apiPost('/api/tasks', payload);
// 同时可让后端兼容：const creditValue = req.body.creditValue ?? req.body.points ?? 0;
严重B2学生提交作业 / 教师快速登记完成 直接 404任务管理
现象

学生端「提交作业」、教师端任务页「快速登记完成」点击后无反应或报错，作业永远显示未完成。

根因

小程序 tasks.js.onQuickComplete 调用 POST /api/completion，且字段为 {task_id, student_id, status}；后端 completions.js 仅注册 POST /api/completion/register，且期望 {taskId, studentIds, status}。路径与字段双重不一致 → 404。

小程序miniprogram/pages/admin/tasks.js:141 apiPost("/api/completion", {task_id, student_id, status})
后端server/src/routes/completions.js:29 router.post("/register", ...) 解构 {taskId, studentIds, status}
修复
// miniprogram/pages/admin/tasks.js — onQuickComplete 改为正确路径与字段
await app.apiPost('/api/completion/register', {
  taskId: this.data.currentTask.id,
  studentIds: [sid],
  status: 'FINISHED'
});
// 学生端提交作业页同理：必须用 /api/completion/register + taskId/studentIds
中B3新增/编辑学生时「学号」丢失学生管理
现象

教师在小程序录入学生姓名+学号，保存后学号栏为空或显示异常，名单导出/按学号检索失效。

根因

小程序 students.js 发送 {name, student_no}，后端 students.js(POST/PUT /) 解构 {name, studentNo}。下划线 vs 驼峰不一致，student_no 被忽略。

小程序miniprogram/pages/admin/students.js (form.student_no / apiPost("/api/students", f))
后端server/src/routes/students.js:107 / :125 解构 { name, studentNo }
修复
// miniprogram/pages/admin/students.js — 字段对齐后端
const payload = { name: f.name, studentNo: f.student_no || '' };
await app.apiPost('/api/students', payload);   // 编辑同理用 studentNo
// 或后端兼容：const studentNo = req.body.studentNo ?? req.body.student_no;
严重B4手动加减积分 直接 400，功能完全不可用积分调整
现象

教师/管理员/课代表在「积分调整」页选择学生、填分数、写原因后提交，提示操作失败，积分不变化。

根因

小程序 credits-adjust.js 发送 {student_id, subject_id, points, reason, type}，后端 creditFlow.js.adjust 解构 {studentId, amount, reason}。student_id→undefined→400「请指定学生」；points→amount=undefined→400「调整分值必须为非0数字」。

小程序miniprogram/pages/admin/credits-adjust.js:81 apiPost("/api/credit-flow/adjust", {student_id, subject_id, points, reason, type})
后端server/src/routes/creditFlow.js:18 解构 { studentId, amount, reason }
修复
// miniprogram/pages/admin/credits-adjust.js — onSubmit 改为后端契约
const val = f.type === 'add' ? Number(f.amount) : -Number(f.amount);
await app.apiPost('/api/credit-flow/adjust', {
  studentId: f.studentId,
  amount: val,
  reason: f.reason.trim()
});
// subject_id / type 后端不需要，删去即可；或后端兼容 student_id/points

六、优化提升点与建议方向

契约一致性（最高优先级）

B1–B4 均属「前端字段名/路径与后端不一致」。建议在工程层面建立共享 API 契约：把后端路由的入参用一份 OpenAPI/JSON Schema 描述，小程序调用层据此生成 TS 类型与请求体，CI 中做契约校验，从根上杜绝此类回归。

请求层健壮性

app.js 的 _api 已做友好错误拦截（好）。建议进一步：① 统一请求/响应字段命名规范（全站驼峰 or 全站下划线，二选一），避免 student_id/studentId 混用；② 对 4xx 业务错误（如 400/403/404）做结构化提示与「重试/联系管理员」引导；③ 列表类接口加 loading 与空态、错误态三态。

鉴权与默认安全

重置密码默认落为 123456（多处在 students.js / users.js）。个人主体小程序上线后，建议：① 首次登录强制改密；② 超级管理员账号 superadmin 仅限本人改密（已做，✓）；③ 操作日志已记录改密/调分，建议登录页增加「忘记密码」走微信身份校验，而非明文默认密码。

并发与数据一致性

积分重算依赖 credit_flow 全量 SUM 后写回 student.total_credits，多位教师/课代表同时给同一批学生登记时存在竞态（非原子）。建议改为单条 SQL 增量更新：UPDATE student SET total_credits = total_credits + ? WHERE id=?，避免并发覆盖。

资源付费墙一致性

GET /api/mp/resources/:id 无条件返回 content（内联重点汇编），仅 url 受广告/积分门槛限制。若产品意图是「看汇编也要消耗积分/广告」，应在返回 content 前校验 adWatched/积分；若意图是「汇编免费、外链资料收费」，则应在 UI 明确区分，避免用户困惑与审核风险。

可观测与灰度

建议小程序端接入轻量埋点（页面曝光、接口耗时、失败率），后台 dashboard 已存在；上线前用「体验版」真机跑一遍 30 人矩阵，重点验证 B1–B4 修复后的加积分/交作业链路。

性能

subjects/students/users 列表为全量返回，30 人 OK，但班级规模扩大后需加分页/虚拟列表；operate-logs 与时间范围筛选已规划，建议尽快落地避免全表扫描。

八、结论

后端业务逻辑本身健康（账号/科目/资料/预警/日志/积分钱包等模块契约一致，100% 通过）。 修复前 85.2% 通过率被 4 个前端契约 bug 拉低，且这 4 项恰好是教师/管理员最高频的核心工作流 （发布作业给积分、学生交作业、加减分、录学号）。修复 B1–B4（均为前端字段名/路径对齐，各约 3 行代码）后，本次复测整体通过率已达 100%。 建议补一份前后端共享 API 契约（OpenAPI/JSON Schema + 生成代码生成），防止再次回归。
